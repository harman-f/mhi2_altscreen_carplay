# A2 storage-path triage — source-verified consumer risks

**Status:** host/source review, not a finished file-migration mapping, installation or target validation. Source baseline: public \`develop\` plus A2 review branch at 2026-11-03. Re-check line numbers whenever the source changes. Machine-readable inventories are emitted by \`tools/release/source_defaults_inventory.py\`, \`storage_migration_review.py\` and \`storage_path_triage.py\` in the publication audit.

## Why the raw hit counts are misleading

The canonical registry has 48 CarPlay keys grouped into **13 file basenames**, and the separately owned broker has 13 revisioned switch files. These 26 records are **in addition to** source lines containing project-root and temporary paths. Literal scanner hits include shell templates, diagnostics, executable scripts, test files and dynamic filename fragments. They must not be counted as unique configuration files or classified as reader/writer roles without source review.

The A2.2 report deduplicates identical literal fragments, distinguishes \`/tmp/mibr-*\` (volatile/IPC/test context) from persistent paths, and separately identifies boot/runtime scripts, source-defined config, release/version receipts, backups and presence markers. \`noncanonical-fragment\` records such as \`%s.conf\`, shell brace remnants and directory prefixes demand exact source reconstruction; they are not real filenames. Dynamic-source records are reviewed as code, not guessed from filename.

## Interpretation of the 18 nonliteral leads

The CI triage separates source lines for environment search paths, persistent-root construction/macros, a mount probe, format-dependent same-filesystem staging, embedded CarPlay launch environment, and text-only usage/comments. **\`#define MIBR_CFG_PERSIST_ROOT\` is active code, not a comment**. A boot script may create a persistent-staging file with a PID suffix; this is not a durable preference. These categories are reviewed leads rather than complete inventories of consumers.

## Required next work: A2.3 exact file ownership matrix

1. Enumerate the full \`alt111_settings_paths\` basename/group reader and writer call graph and all navigation-shell \`ROOT\` expansions. Verify generated script contents and installed hooks, not only source templates.
2. For each persistent source and target, identify exactly one authoritative writer, all readers (including legacy binary/Java), format/magic/revision/CRC, precedence/default, lifecycle, selected three-firmware target integration and specific backup/rollback/uninstall path.
3. Identify interactions with existing migrations, dangerous *absence-as-ON* or *presence-as-OFF* markers and exact early boot branches. Reject mixed legacy/new formats, collisions or concurrent independently writable stores.
4. Establish format-aware conversion and negative interrupted-write/readback/RO tests in a subsequent PR. **Do not perform an on-unit move, change any default or qualify any firmware from this A2.2 source analysis.**
