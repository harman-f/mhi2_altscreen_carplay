## Transport and responsibility
ClientAppender$ClientConfigurator.readUTF expects Java DataOutputStream.writeUTF("VersionInfo client=1.3.17"). ClientAppender.wrongClientVersion compares parsed major*1000+minor with Version.getVersion() (1003). isClientLibCorrect() returns false in this supplied version: server sends @d + U64 BE library length + LF then exactly the bzip2 library bytes. Client discards the bytes and sends writeUTF(">OK<"). Only after OK is the node registered for outgoing trace and its rolling buffer flushed; a welcome @m frame and raw ITraceEvent.writeBytesTo plus LF may follow. The 60-second watchdog explains previous no-send receiver: 0 bytes before the server closes. New mibr-dsi-rx R2.1 transmits ONLY those two mandatory appender handshake messages; no controller command, emulator activation, key replay, DSI request, persistence, or OEM JAR write. Peer IP is fixed to 127.0.0.1, port 1800 by default. Captures binary POST-HANDSHAKE APPENDER transport on SD; no false event-level timestamp attribution. OEM library is verified by BZh magic but NOT persisted. Hard caps: 16 MiB library, 16 MiB trace, 45 s handshake. Failure report includes phase and progress.

## Exact Java interface expectations (uncompressed client library, javap)
The active six scopes correspond to generated de.audi.tghu.dsitrace.client.Transport_* adapters and org.dsi.ifc.* request/reply interfaces. Full mode traces methods with arguments, whereas small mode only method name per uploaded trace config. Such calls are observed when they occur, not a full bootstrap UI-dump or arbitrary introspection. Direction and existence in firmware must be validated in a live trace.

1. DSIBAP: request(int,int,int,int,int), requestVoid, requestByteSequence(int,int,int,byte[]), requestError; listener indication(...), indicationVoid, indicationByteSequence(...,byte[]), indicationError, acknowledge. Useful to correlate HU-side BAP function activity and payload/ACK with VC operations. No immediate guarantee that all external J794→J285 BAP frames are instrumented at this layer. Byte arrays need offline protocol mapping.
2. DSICarKombi: highly promising *configuration/data* rather than graphics. Commands setDCDisplay1/2/3MainSelection(DCMainItems), setDCActiveDisplayPreset(int), setDCDisplayViewConfiguration(DCDisplayViewConfiguration), requestDCDisplayPresetsList, requestDCElementContentSelectionList, setBCMenueConfig(BCMenueConfiguration,int); listener updateDCDisplay1/2/3MainSelection, updateDCActiveDisplayPreset, updateDCDisplayViewConfiguration, updateDCViewOptions, responseDCDisplayPresetsList and element-list responses. DCMainItems includes navigation/audioMedia/telephone/tripScreen/carMain/individual and others as **boolean built-in slots**. DCDisplayViewConfiguration has a numeric activeDisplayView. DCDisplayPresetsListRecord exposes pos/state/type/instance and display1/2/3, whose mainSelection and additional-info fields are typed. BCMenuConfiguration contains built-in configurable drive statistics switches. THIS IS NOT PROOF of dynamically injecting an arbitrary named VC menu node.
3. DSIFastListScrollingAudio: listener indicationMediaBrowser and indicationMediaBrowserJobs; counterpart responseMediaBrowser, responseMediaBrowserArray, pushCommonList(DataCommonList[]), pushReceptionList, pushCurrentListSizeAudio. Can correlate list window/index/count/item responses to roller actions in OEM radio/media mode; not guaranteed to be the source of main VC menu navigation.
4. DSIFastListScrollingNavigation: indicationNavBook, indicationGetInitialsNavigation, indicationNavBookJobs, responseNavBook, responseNavBookArray(DataAddress[]), pushLastDestList, pushUpdateFavoriteDestList, pushCurrentListSizeNavigation. Mainly destination book/history/list metadata, not inherently the navigation video layer nor CarPlay map zoom.
5. DSIFastListScrollingTelephone: indicationPhonebook, indicationPhonebookJobs, responsePhonebook, responsePhonebookArray(DataPhonebook[]), pushupdateFavoriteList and pushCombinedNumbers. May reveal whether a phone/CarPlay-mode transition stimulates native phone-list requests, but the *absence of a visual menu* alone proves neither a missing data provider nor absent menu configuration.
6. DSIKombiPictureServer: setKombiHmiReady, indicationCoverArt/StationArt/ActiveCallPicture/DynamicIcon/PictureStream, responseCoverArt(ResourceLocator), responseStationArt, responseDynamicIcon and responsePictureStream(...,byte[]). Images/icon metadata and potentially pixel/image payloads, not the 110/111 raw MOST graphics transport.

## Proposed discriminating test and stop criteria
Use native v1.4 KeyPanel logs and DSI trace in one bounded 240 s session. Distinct manual NOTE before: idle, NAV native, R roller ±3 ticks, VC main MENU, audio list scroll, telephone menu, driving data, VIEW preset change, CarPlay 111 active and R roller ±3 ticks, then native 110 return. Time-match encoder (already proven DSIKeyPanel updateEncoder2 KBD4 encoderId40 increments ±1 validity1) with typed DSI method changes. Set a focused pass/fail matrix:
- HANDSHAKE PASS, lib_bytes≈818851, ok_sent=1 means transport works (not evidence of DSI data yet).
- post_handshake raw bytes>0: trace transport proven; parse @m welcome vs event binary OFFLINE with OEM client decoder. Do not equate @m-only bytes to useful DSI calls.
- correlate native VC VIEW with updateDCActiveDisplayPreset / updateDCDisplayViewConfiguration and request/response with MENU. If none occur while user observes changes, reevaluate whether these changes are HU-side, cluster-side, or via an unselected scope.
- search DSIBAP operation/bytes and fastlist exchange near native menu changes; stable counterfactual idle window.
- In CarPlay 111 compare wheel event with DSI result; even a correlated call is only an observation and not a validated hook or zoom control.

Privacy: full-mode nav/phone arrays and raw trace may include addresses, phone numbers and contacts. Keep private; release aggregate counts and sanitized method names only.
